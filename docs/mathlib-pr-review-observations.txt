MATHLIB4 PR REVIEW — OBSERVED EXAMPLES AND TACIT KNOWLEDGE
==========================================================

Source: leanprover-community/mathlib4, GitHub API, sampled 2026-08-04.
~3000 inline review comments, ~1600 PR-conversation comments, plus full threads for
~30 closed-unmerged PRs and review-submission bodies for ~14 heavily-reviewed PRs.
Quotes are verbatim; PR numbers and reviewer handles are given so each can be checked.
This file records what reviewers actually said, not a style guide.

1. AI DISCLOSURE — the single most frequent first contact with a new PR
--------------------------------------------------------------------------------

Triage has a canned opener, posted verbatim many times per week:

  "Hello from triage! Can you comment on whether you used AI for this project? Thanks!
   (Per mathlib's AI policy, this is not forbidden in principle, but its usage must be
   disclosed.)"
      — grunweg, on #42035, #42040, #39369, #42286, #42293, ...

Follow-up when the answer is vague:

  "I see. Can you comment on *how* you used AI, and also say so in the PR description,
   please? This scale [visidata self-assessed AI level] provides some categories that
   may be helpful."
      — grunweg, #42040

  "@SNAPKITTYWEST if you are using AI for your PR (which very much looks like the case),
   you must disclose it."
      — felixpernegger, #41754

  "Large parts of this PR, including the description, appear LLM-generated. Can you
   comment on your use of AI here?"
      — b-mehta, CHANGES_REQUESTED on #39307

Disclosure is also enforced on the *comments*, not just the code:

  "Moderation note: @AlyciaBHZ At least two of your comments above look AI-generated.
   Using LLMs to write comments (on Github or on Zulip) is against community rules.
   Please use your own words instead. Consider this an official warning."
      — grunweg, #42293

A disclosure that reviewers reacted well to (it says what was checked by hand):

   - `lake build ...`, `lake exe runLinter ...`, `lake exe lint-style ...`

     relation that is locally confluent but not confluent"

16. PR DESCRIPTIONS — what reviewers reward and punish
--------------------------------------------------------------------------------

Template facts (`.github/PULL_REQUEST_TEMPLATE.md`):
  - PR title becomes the first line of the squashed commit message.
  - Text ABOVE the `---` is appended to the commit message; text below is GitHub-only.
  - `Co-authored-by: Name <email>` lines go directly before the `---`.
  - Moves/Deletions are declared in the commit message:
        Moves:
        - Vector.* -> List.Vector.*
        Deletions:
        - Nat.bit1_add_bit1
  - Dependencies are declared as `- [ ] depends on: #abc`.
  - "note that most reviewers will only notice your PR if it passes the continuous
     integration checks."

Title conventions seen on every merged PR: `feat(Area/File): ...`, `chore(...)`,
`refactor(...)`, `perf(...)`, `fix(...)`, `doc(...)`. Bors rewrites merged titles to
`[Merged by Bors] - <title>`.

--------------------------------------------------------------------------------
20. SHORT LIST OF WHAT GETS A PR MERGED, AS THE THREADS SHOW IT
--------------------------------------------------------------------------------

  - CI green first; reviewers mostly don't look before that (stated in the PR template).
  - Small. Series of ≤300-line PRs beat one 2000-line PR, and authors are told so.
  - Nothing in it already exists in mathlib, Batteries, or adjacent Lean repos — and the
    description says what search was done.
  - Names follow convention and describe the statement, not a person; namespace + name is
    not absurdly long; no gratuitous primes; instances usually unnamed.
  - Hypotheses are as weak as the proof allows; universes/index types generalized where free.
  - Docstrings add information not readable off the type signature.
  - Imports are minimal, alphabetized, `public import` used correctly, and any import
    increase is justified in the description.
  - Renames/removals carry `@[deprecated (since := "<today>")]` (plus `to_additive`).
  - `set_option ... in` and `#adaptation_note` are treated as debt: root-cause them or
    comment them.
  - Every reviewer suggestion is either applied or answered with a concrete reason.
  - AI use disclosed in the description, in specific terms, including which checks the human
    ran by hand.
  - Design disagreements are taken to Zulip and linked back, rather than argued in the diff.
